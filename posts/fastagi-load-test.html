동시 90통, 첫 안내 대기를 20.9초에서 4.6초로

전화 한 통으로 출근을 기록하는 서비스에서, 전화가 몰릴 때의 대기 시간을 미리 측정하고 78% 줄인 과정입니다.

2026년 10월 · Asterisk · FastAGI · Python

요약
  • 출근 시간 몰림을 교환기 안에서 동시 90~300통으로 재현하고, 0.2초 단위로 단계별 시간을 측정했습니다.
  • 병목은 안내 재생이 아니라 통화마다 스크립트를 띄우고 연결을 새로 맺는 구간이었습니다.
  • 상주 FastAGI 서버 + 커넥션 풀 + 자동 대체 경로로 최대 대기 20.9초 → 4.6초, 동시 300통까지 끊긴 통화 0건.

왜 대기 시간을 측정했나

어르신이 출근 번호로 전화를 걸면 교환기가 받아 "○○○ 님, 출근되었습니다"라고 안내합니다. 출근 시각에는 이 전화가 한꺼번에 몰립니다. 출근 기록이 제대로 남아도, 전화를 받은 뒤 아무 소리가 없으면 어르신은 끊긴 줄 알고 다시 걸거나 그냥 끊습니다. 그래서 큰 행사 전에 "전화가 몰리면 첫 안내까지 얼마나 기다리는지"를 측정하기로 했습니다.

테스트 환경

  • 외부 회선을 쓰지 않고 교환기 안에서 Local 채널로 가상 통화를 만들었습니다. 테스트 기관에 가상 참여자 300명을 두고, 테스트용 출근 번호로 전화하게 했습니다.
  • 교환기 로그만으로는 단계별 시각을 알 수 없어서, 0.2초마다 core show channels concise를 실행해 각 통화가 스크립트 실행 중인지, 안내 재생 중인지를 시간과 함께 기록했습니다.
  • 주의할 점: 테스트용 다이얼플랜을 dialplan add로 넣을 때 앱 인자에 공백이 있으면 그 줄이 오류 없이 빠집니다. 공백 없는 형태로 넣어야 합니다.

끊긴 통화는 없었고 출근도 모두 기록됐습니다. 안내 재생 자체는 느려지지 않았고, 지연은 통화마다 파이썬 스크립트를 새로 실행하고 서버에 HTTPS 연결을 새로 맺는 구간에서 생겼습니다. 교환기 밖에서 파이썬 프로세스 90개만 동시에 실행해 봐도 마지막 프로세스는 16초 뒤에야 시작됐습니다.

개선한 것

  1. 상주 서버(FastAGI) — 통화마다 스크립트를 실행하지 않고, 미리 떠 있는 서버가 교환기 요청을 받습니다.
  2. 연결 풀 — 출근 API로 가는 연결 40개를 미리 열어 둡니다. 점검 작업이 30초마다 오래 쉬고 있는 연결을 확인하고, 10분이 지난 연결은 새로 맺어 서버 주소가 바뀌어도 따라가게 했습니다.
  3. 대체 경로 — 상주 서버에 문제가 생기면 다이얼플랜이 기존 스크립트로 자동 전환합니다. 서버의 응답을 받기 전에 실패한 경우에만 전환해서, 출근이 두 번 기록되지 않게 했습니다.
  4. 통화 중에는 다이얼플랜을 다시 불러오지 않기 — 다시 불러오는 순간 우선순위가 바뀌어 엉뚱한 경로로 가는 것을 검토 중에 발견했습니다. 배포 스크립트는 진행 중인 출근 통화가 있으면 기다립니다.

연결 풀까지 붙이자 처음 거는 전화는 최대 4.0초였지만, 이미 출근한 분이 다시 걸면 6.1초까지 늘었습니다. 출근 API가 초당 처리할 수 있는 양에 맞춰 동시 처리를 40으로 묶었고, 중앙값은 2.8초에서 4.0초로 늘었지만 어떤 경우든 4.6초 안에 들어왔습니다. 중앙값을 조금 내주고 가장 늦게 안내를 듣는 분의 대기를 줄인 선택입니다. 어르신 서비스에서는 평균보다 최악의 경우가 첫인상이 되니까요.

한계 지점 찾기 — 300통까지

90통에서 멈추지 않고 어디서 깨지는지 끝까지 밀어 봤습니다. 200통에서 교환기가 Too many open files를 냈고, 프로세스가 열 수 있는 파일 수(1,024)가 한계였습니다. 재시작 없이 실행 중인 교환기의 한도를 올리고 설정에도 반영한 뒤 다시 측정하니 200/200, 300/300(중앙값 2.4초)으로 모두 처리됐습니다.

배운 점

  • "느리다"는 단계별로 나눠 측정하면 원인이 보입니다. 이번 원인은 음성이 아니라 프로세스 생성과 연결이었습니다.
  • 평균보다 최대를 봅니다. 가장 늦게 듣는 사람이 서비스의 첫인상입니다.
  • 새 구조에는 항상 기존 방식으로 돌아갈 경로를 남깁니다.
