동시 통화 부하 시험 — 첫 안내까지 20초를 4초대로

전화 한 통으로 출근을 찍는 서비스에서, 전화가 몰릴 때 생기는 침묵을 미리 재고 줄인 기록입니다.

2026년 10월 · Asterisk · FastAGI · Python

왜 '침묵'을 쟀나

어르신이 출근 번호로 전화를 걸면 교환기가 받아 "○○○ 님, 출근되었습니다"를 들려줍니다. 출근 시각엔 이 전화가 한꺼번에 몰립니다. 출근 기록이 제대로 남아도, 받은 뒤 아무 소리가 없으면 어르신은 끊긴 줄 알고 다시 걸거나 그냥 끊습니다. 그래서 큰 행사 전에 "몰리면 첫 안내까지 얼마나 조용한가"를 재 보기로 했습니다.

시험 꾸리기

  • 바깥 회선을 쓰지 않고 교환기 안에서 Local 채널로 가짜 통화를 만들었습니다. 시험 기관에 가짜 참여자 300명을 두고, 가짜 출근 번호로 걸게 했습니다.
  • 교환기 기록만으로는 단계별 시각이 안 보여서, 0.2초마다 core show channels concise 를 떠서 각 통화가 스크립트 실행 중인지, 안내 재생 중인지를 시간으로 남겼습니다.
  • 함정 하나: 시험용 다이얼플랜을 dialplan add 로 넣을 때 앱 인자에 띄어쓰기가 있으면 그 줄이 오류 없이 빠집니다. 띄어쓰기 없는 꼴로 넣어야 합니다.

끊긴 통화는 없었고 출근도 전부 찍혔습니다. 하지만 안내 재생 자체는 늘어지지 않았고, 늘어지는 곳은 통화마다 파이썬 스크립트를 새로 띄우고 서버에 HTTPS 연결을 새로 맺는 구간이었습니다. 교환기 밖에서 파이썬 프로세스 90개만 한꺼번에 띄워 봐도 마지막 것이 16초 뒤에야 시작했습니다.

고친 것

  1. 상주 서버(FastAGI) — 통화마다 스크립트를 띄우지 않고, 미리 떠 있는 서버가 교환기 요청을 받습니다.
  2. 연결 미리 맺기 — 출근 API 로 가는 연결 40개를 미리 맺어 둡니다. 지키미가 30초마다 오래 쉰 연결을 깨우고, 10분 넘은 연결은 새로 맺어 서버 주소가 바뀌어도 따라가게 했습니다.
  3. 넘어가는 길 — 상주 서버가 멈추면 다이얼플랜이 예전 스크립트로 자동으로 넘깁니다. 서버의 답을 받기 전에 실패했을 때만 넘겨서, 출근이 두 번 찍히지 않게 했습니다.
  4. 통화 중엔 다이얼플랜을 다시 읽지 않기 — 다시 읽는 순간 우선순위가 밀려 엉뚱한 줄로 가는 걸 검토에서 찾았습니다. 바꾸는 스크립트는 출근 통화가 하나라도 있으면 기다립니다.

마지막 줄에서 가운데값은 오히려 늘었습니다. 서버가 한꺼번에 받을 수 있는 양 안에서 가장 늦게 듣는 분의 침묵(최대)을 줄이는 쪽으로 맞바꿨기 때문입니다. 어르신 서비스에서는 평균보다 최악이 중요합니다.

더 올려 200통을 걸자 교환기가 Too many open files 를 내며 일부 통화를 안내 없이 끝냈습니다. 프로세스가 열 수 있는 파일 수(1,024)가 끝선이었습니다. 재시작 없이 돌고 있는 교환기의 한도를 올리고 설정에도 남긴 뒤 다시 재니 200/200, 300/300(가운데 2.4초)로 모두 처리됐습니다.

배운 것

  • "느리다"는 단계별로 잘라 재면 범인이 보입니다. 이번엔 소리가 아니라 프로세스와 연결이었습니다.
  • 평균보다 최대를 봅니다. 가장 늦게 듣는 사람이 서비스의 얼굴입니다.
  • 새 구조에는 언제나 예전 길로 넘어가는 문을 남깁니다.
