아키텍처 — 두 가지 연결 방식

A 방식은 교환기의 음성을 브리지 서버가 받아 웹소켓으로 음성 AI에 넘기고, B 방식은 교환기가 음성 AI에 SIP로 바로 붙습니다. 같은 가상 고객 시나리오로 두 방식을 측정해 A를 기본, B를 예비 경로로 운영합니다.

  1. 고객 전화수신 · 발신
  2. SIP 중계 (Kamailio)번호로 경로 찾기
  3. 교환기 (Asterisk)녹음
  4. A · 웹소켓 브리지 (기본)B · SIP 직결은 예비
  5. 음성 AI대화 · 판단

핵심 기여

1. 응답 지연 72% 단축 — 5초 → 1.4초

문제
처음 SIP로 연결했을 때, 고객의 말이 끝나고 AI가 대답하기까지 약 5초가 걸렸습니다. 전화에서 이만큼 조용하면 사람은 끊습니다.
원인
같은 녹음을 웹소켓으로 흘려 재현하자 5.1~5.6초로 같았습니다. 병목은 전화망이 아니라 발화 종료 감지 설정이었습니다.
해결
발화 종료 감지를 조정하고, 두 연결 방식을 같은 시나리오(인사·끼어들기·머뭇거림·침묵 × 2회)로 측정하는 벤치마크를 만들었습니다.
판단
맞장구 뒤 응답까지 견주니 A는 1.2~1.4초, B는 2.0~2.4초였습니다. 운영 경로는 A로 정하고, B는 장애 대비 예비로 남겼습니다.
결과
응답 지연 5초 → 1.4초 (A 1.44초 · B 1.75초).

2. 사람처럼 듣는 대화 — 상황별 테스트 57 → 71/72

문제
사람은 통화 중에 "아, 네" 같은 맞장구를 칩니다. 테스트 통화에서 AI가 맞장구에 말을 멈추고 인사부터 다시 하는 경우를 찾았습니다.
해결
맞장구 표현 17개는 끼어들기로 보지 않고, 소개가 끊기면 "이미 들었으니 이어 가라"는 맥락을 바로 넘깁니다. 대답이 없으면 한 번만 확인하고, 계속 없으면 정중하게 마무리합니다.
판단
매번 실제 전화를 거는 대신 텍스트로 상황을 재현하는 테스트를 먼저 돌리고, 실제 전화 점검은 꼭 필요한 몇 통만 걸어 비용과 시간을 줄였습니다.
결과
상황별 대화 테스트 57 → 71/72 · 실제 교환기 점검 39/39 · 같은 말 반복 0건.

3. 자동응답 판별 — 규칙 + LLM, 섀도 모드로 안전하게

문제
목록 순서대로 전화를 걸면 자동응답이나 음성사서함이 받기도 합니다. 기계에 대고 상담을 끝까지 하지 않도록, 받는 쪽부터 가려야 했습니다.
해결
실제 통화의 첫마디 971건으로 판별 규칙을 만들고, 규칙이 판단하지 못한 경우만 LLM 확률 판정(0.9 이상)으로 보완했습니다.
판단
새 판정이 바로 통화를 끊게 하지 않고 섀도 모드로 붙였습니다. 판정은 기록만 하고, 운영 데이터로 정확도를 계속 확인하면서 적용 범위를 넓힙니다.
결과
규칙만 썼을 때 정밀도 99.6% · 재현율 90.5% → 규칙 + LLM 재현율 93%, 사람을 기계로 오판한 경우 1건.

4. 7만여 건 발신 엔진 — 규칙을 넘기 전에 스스로 멈춤

해결
번호당 한 번만 걸기, 야간 발신 금지, 동시 통화 수 제한, 사용량 한도에 가까워지면 발신 전 자동 정지를 엔진에 넣었습니다. 시작과 중지는 고객사 화면에서 직접 할 수 있습니다.
결과
운영 규칙을 코드로 강제하는 안전한 대량 발신.

회고

  • "방식이 문제"라는 가설은 같은 조건으로 재현해 검증합니다. 이번 지연의 원인은 전화망이 아니라 설정 하나였습니다.
  • 음성 AI의 판단은 '선택'보다 확률로 받아야 통화를 끊을지 안전하게 정할 수 있습니다.
  • 새 판단 로직은 섀도 모드로 먼저 붙여 운영 데이터로 확인합니다.
